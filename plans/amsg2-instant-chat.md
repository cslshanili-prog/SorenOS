# 主動消息 2.0「即時對話」方案（instant chat）

> 討論稿。定位：把聊天主路徑從「瀏覽器本地跑生成」換成「雲端跑生成」，
> 複用主動消息 2.0 已有的整條管線。少寫實現，多寫取捨——先把方向釘死再動手。

## 一句話

把每條聊天消息當成一條「立刻觸發」的主動消息任務：按下發送 = 一次很小的
POST 上雲，生成在用戶自己的 CF Worker 裡跑完，結果走 Web Push 下發。
客戶端發完那一刻就自由了——切後台、殺進程都行，回覆到了推送會叫它。

## 為什麼要做

現狀的聊天路徑要求**客戶端從發送活到生成結束**，由此背上三個包袱：

| 包袱 | 現狀 | 改完 |
|------|------|------|
| fire_pack 補傳 | 打髒後微任務內立即上傳，同一輪的連環打髒合併成一次 | 機制整個退役——上傳發生在按發送那一刻，前台必然可見 |
| presence 心跳 | 生成期間每 15s 兩個請求，請求數正比生成時長（等 2 分鐘 ≈ 20 個請求） | 歸零——worker 自己知道這輪在跑，不需要客戶端舉手 |
| 生成期間被殺 | 切後台幾秒就可能被殺，這輪白等 | 無所謂，雲上照跑，回來收推送 / 拉收件箱 |
| 走 Deno 門面的額度 | 未驗證組織 1 萬請求/月 ≈ 每天 17 輪（按 2 分鐘生成算） | 每輪 1 個請求 ≈ 每天 330 輪 |

這個方案是把包袱直接卸掉。

## 設計要點（高層）

1. **觸發**：新端點，POST 帶上增量消息 + 本地游標（最後一條消息 id + 條數），
   worker 回 200 = 已受理，幾十毫秒的事。門面的 105s 首字節、SSE 送達判定
   那些約束全都不再適用——沒有任何一條長連接。
2. **生成**：先落盤再開跑，雙保險。POST 把一條「立即執行」任務寫進 D1
   （落盤即受理），同一個請求裡 `ctx.waitUntil` 馬上跑生成；isolate 被
   回收的話，cron 下一分鐘撿起仍 pending 的行接著跑。任務行帶認領標記
   （認領時刻超時才允許 cron 接手）防雙跑。體感：waitUntil 活著 = 秒開跑，
   死了 = 最壞 +60s，正確性兩頭都兜住，不依賴對平台行為的預判。
3. **生成管線**：複用主動消息 2.0 fire 現有那套——工具循環、表情包、
   實時世界、後台 MCP 都是現成的。**這次 POST 順手把 fire_pack 也更新掉**，
   到點的定時任務和即時對話共用同一份上下文，補傳機制才真正退得掉。
4. **送達**：Web Push（CF 直發手機，不過門面）。通知一定彈，但同一個角色摺疊成
   一條，用戶看著頁面時不響、切後台照常響鈴；消息本身照舊由 SW 轉給頁面上屏；
   推送丟了靠上線拉收件箱兜底
   ——收件箱進來後那條 13 步後處理管線是現成的，記憶宮殿等本地後處理照跑。
   上屏體感不變：管線對「剛送達」的消息保留擬人打字節奏（每條氣泡之間
   0.5~2s），只有補收（躺超過 2 分鐘）才一次性回填，和現在的前端一致。
5. **狀態**：D1 存對話歷史，但**本地仍是唯一真相**。每次 POST 只傳增量，
   worker 用游標對帳，對不上（回滾備份、刪改消息）就要求整包重傳，
   重傳走 gzip 上行（大 body 42s 超時的教訓已有現成修法）。
6. **失敗**：雲端生成失敗推一條 `messageKind: 'error'`（SW 已有這條分軌）；
   客戶端「正在輸入」有超時兜底，到點提示失敗、可手動重發。

## 已經定下的取捨

- **無流式**。生成期間沒有逐字吐出，配「正在輸入…」指示：POST 200 亮起，
  push 到達熄滅。等不到就每 60s 去雲端點名問一次那條任務的狀態，只有雲端明確
  說它已失敗（或那行沒了而回復也取不回）才熄燈、提示可重發；雲端還在跑或在
  重試就一直等。回覆到端後按打字節奏逐條上屏（見上），體感更像真人回消息。
- **通知一定彈，打擾靠摺疊 + 按可見性靜音壓**：同一個角色在通知欄裡只留最新
  一條（同 tag 互相覆蓋）。響不響由 SW 收到推送那一刻的窗口可見性定
  （`silent: 'when-visible'`）：用戶正看著頁面就安靜躺著，切後台、鎖屏則照常
  響鈴震動。同 tag 默認是靜默替換，所以每一輪的第一段帶 `renotify`，一輪響一
  聲、後面幾段安靜更新內容。訂閱是按 `userVisibleOnly` 建的，收到 push 卻不彈
  等於跟瀏覽器違約——Firefox 按配額把訂閱退掉、iOS 過了新訂閱的幾天寬限期一條
  就吊銷，兩邊都靜默發生。所以口徑是：要推就一定彈，不想彈的內容壓根不發推送、
  留在服務端收件箱等客戶端上線補拉。
- **不做靜默兜底**。顯式開關，關掉回本地生成。POST 失敗 = 這條沒發出去，
  明確報錯、可手動重試，絕不悄悄轉回本地跑——靜默分流那種查無可查的坑
  踩過一次就夠了。
- **聊天 API 憑據常駐雲端**。AI 模式定時任務本來就這樣，即時對話只是讓
  每一輪都用它，不是新增暴露面。
- **單用戶、單設備假設不變**。
- **開關前置條件**：推送權限已授予才允許打開（不然發得出、收不到），
  沒給權限時開關置灰並說明。
- **一次做完整替換，不分階段發**。amsg2 整條鏈路已經端到端驗證過，
  沒有需要分批探路的未知數；下面的施工順序只是幹活的先後，不是一個個
  可發佈的里程碑。

## 施工順序

1. worker 側通道：新端點 + 立即任務行 + `waitUntil` / cron 雙保險 + 認領防雙跑
2. 對帳與並軌：游標 / 全量重傳（gzip）/ fire_pack 由這次 POST 順手更新；
   退役 presence 心跳和 fire_pack 補傳
3. 前端切換：發送路徑改走 POST、「正在輸入」指示、通知摺疊與靜音策略
4. 收尾：設置頁開關（含置灰）、文檔、埋點

## 待查小項（不擋工）

- 已定：群聊不切（收件箱按 charId 路由，群聊沒有 charId，見契約「群聊不動」條），繼續走本地生成
- 已定：即時對話是聊天上雲的唯一路徑。
- 那條摺疊通知在 iOS 真機上的觀感：前台聊天時（該安靜躺著）和切後台時（該響鈴叫人）
  兩種情況都要看，另外確認 iOS 認不認 `renotify`——不認的話新一輪的第一段還是會被
  當成靜默替換

## 明確不做

- 流式吐字（沉默期由「正在輸入」承擔）
- 任何靜默回退本地的邏輯
- 多設備同步
