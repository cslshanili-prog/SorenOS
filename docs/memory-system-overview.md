# 記憶系統概覽

本項目包含兩套並行運行的記憶系統：傳統日度/月度總結（Legacy）和向量化記憶宮殿（主系統）。

### APK 中導出記憶宮殿

安卓「導出為 JSON」與設置的全部備份共用 `shareOrDownloadBlob`，直接打開系統分享面板，由用戶選擇保存或發送的應用；大型文件分片寫入分享緩存，不額外寫入公共文檔目錄。取消分享不記作成功，不將應用緩存誤稱為已保存的備份。網頁仍走瀏覽器分享/下載。實現見 `utils/memoryPalace/saveExport.ts`。

### 可選的相對時間補註

全局配置 `relativeTimeAnnotations` 嚴格默認關閉；缺失、false、非法配置均不啟用。不啟用時，提取請求不增加來源編號或提示詞、不生成 `relativeTimeAnchor`，正文和召回保持原樣。

開啟後，私聊手動/自動共用提取入口只為具有有效 `relativeTimeSource` 消息編號、且相對措辭匹配原消息的節點保存來源日期（設備本地日期 key，獨立於 createdAt 事件日）。跨消息不同參照日要求模型拆分；無可靠來源時不猜。來源識別仍依賴提取模型。編輯頁只讀展示參照日與補註，用戶只能修改原文措辭或直接寫明具體日期，不提供日期編輯控件；舊記憶無來源日期時不補註。

`relativeTime.ts` 根據原文動態生成補註片段，宮殿列表/詳情/編輯預覽與召回共用規則。原始 content 不混入系統文字，開關不寫節點、不調用 API、不重新向量化。紫色日期只讀；修改相對措辭後自動計算，直接改寫為具體日期則不再補註，無剩餘相對措辭時編輯保存清除關聯。用戶原有日期括號保留。昨天/前天/阿拉伯及中文數字天數按日曆日計算，上週按七天前左右，上個月/數字個月前只標年月，去年只標年份。參照日期固定，不隨當前日期或用戶時區變化重建。

只補活節點（含盒內活節點及便利貼），不補 isBoxSummary 或 archived 節點；封盒二次總結仍讀取原文，不把補註烘焙進摘要。開啟後的宮殿 JSON 導出 content 包含補註，同時通過 relativeTimeExport.originalContent 保存原文（向量仍對應原文）；導入驗證補註與原文相符後恢復原文，保持開關可逆。外部修改過導出正文則尊重修改，不恢復舊原文，也不復用舊向量。關閉時導出格式及正文保持原狀。神經鏈接的關聯記憶文本導出也帶補註，日常編輯仍讀取原文；不關聯的傳統記憶不變。整機備份繼續保存原始節點及來源字段，不改備份恢復邏輯。

### 神經鏈接：新自動歸檔關聯宮殿，舊檔案保持原樣

神經鏈接繼續使用同一個 MemoryArchivist，原有日度/月度組織、導入清洗和文本導出保持不變。不遷移舊數據，不另設宮殿列表或舊檔案界面。

從本次更新起，常規 processNewMessages 成功存儲的節點生成帶 palaceMemoryId 的 MemoryFragment，每個節點一條，summary 保留當時正文作為傳統模式/源節點缺失的兜底。新鏈接按源 ID 去重，不合併到同日舊快照；舊導入、歷史缺口修復仍生成原來的無鏈接記錄，不追溯綁定。

向量化保存安全：vectorizeAndStore 在寫入前驗證返回向量完整性，去重後由 MemoryNodeDB.saveVectorizedMany 將整批正文和向量放入同一事務；失敗整批迴滾，成功後才通知界面並上傳遠程向量。自動歸檔在推進水位前讀取實際落庫節點，因此去重跳過的候選不會形成懸空關聯。

宮殿開啟時，神經鏈接通過顯式 ID 讀取最新正文；編輯共用 updateStoredMemoryNode，正文變更更新向量。導出前重新解析這些鏈接，輸出仍是原來的文本格式；導入仍寫普通檔案，不自動向量化。刪除神經鏈接條目只移除檔案引用，不刪除宮殿源節點，確認窗會說明。

宮殿關閉時使用保存的檔案文本，原有總結流程繼續可用。此時編輯關聯記錄會將其轉為獨立傳統記錄，重新開啟宮殿也不會覆蓋該修改。宮殿源節點缺失時保留檔案文本兜底，不刪除檔案。節點變更事件只刷新明確關聯的新記錄，不改動舊檔案。

宮殿手動刪除單條記憶（含批量刪除中的各條）時，若日度檔案存在顯式關聯，詢問是否同步刪除：選擇「是」刪除關聯檔案；選擇「否」只移除 palaceMemoryId，完整保留檔案原有 summary，成為獨立傳統記憶；取消彈窗則不刪除本條。源節點與檔案處理在同一 IndexedDB 事務提交，隨後發出增量事件更新 OSContext。無關聯的舊檔案不做內容匹配或推測。整庫清空仍走原有獨立流程。

## 系統一：傳統日度/月度總結

### 數據結構

- `memories: MemoryFragment[]` — 每日記錄（date + mood + summary）
- `refinedMemories: Record<string, string>` — LLM 生成的月度精煉總結
- `activeMemoryMonths: string[]` — 哪些月份的詳細日誌要注入上下文

### 輸入

- **日度記錄**：`MemoryFragment`，含 `date`、`mood`、`summary`
- **月度總結**：用戶在 `MemoryArchivist` 組件手動點"生成"→ `handleRefineMonth()` 將該月所有日度記錄送給 LLM 做精煉（temp=0.3）

### 調用/輸出（context.ts → ContextBuilder）

- `buildRoleSettingsContext(char)`（用於情緒評估）：注入全部月度總結 + 當月日度記錄
- `buildCoreContext(char, user, true)`（用於聊天）：
  - 月度總結 → "長期核心記憶"
  - `activeMemoryMonths` 對應的詳細日誌 → "激活的詳細回憶"
- AI 可以用 `[[RECALL: YYYY-MM]]` 語法主動拉取某個月的詳細日誌

### 管理

- 用戶可切換哪些月份"激活"（控制 token 用量）
- 可編輯/重新精煉月度總結

## 系統二：向量化記憶宮殿（主系統，仿大腦結構）

### AI 原文範圍（各入口共用）

`utils/chatContextRange.ts` 是角色原文可見範圍的唯一入口：

- **自適應**：讀取記憶水位線之後的原文，忽略殘留的手動 `contextLimit`；200 / 100 等檔位決定整理節奏，不是發送條數的硬上限。
- **手動**：從完整私聊庫取最近 `contextLimit` 條，包括已歸檔原文；不再先用宮殿水位線截斷。
- 用戶設置的額外起點只能收窄有效範圍，過期起點自動失效。
- ChatApp 的 `loadCharacterContextRange` / `computeContextRangeSnapshot` 保持原設計；其他入口直接複用。統一載荷層還會把 UI 提供的 `recentMsgsHint` 與實際可見消息取交集，防止召回、世界書掃描或識圖旁路讀到範圍外原文。`utils/contextEntryParity.test.ts` 對照 ChatApp 與見面發送、重寫和感知的最終原文列表驗證一致性。
- 需要讀取角色近期原文的 AI 功能調用 `loadCharacterContextMessages`；已有完整候選快照時調用 `selectCharacterContextMessages`。聊天、見面（含感知/重寫）、通話、劇情角色記憶輸入、查手機、日程、彼方、小屋、桌面互動、活動和主動消息等採用同一邊界。
- 某個功能明確只需近期片段或設有獨立取樣條數時，在上述範圍**以內**取樣，不能借此讀取被用戶隱藏的原文。劇情本身的獨立歷史和群聊公共歷史仍有各自的範圍規則。
- 瀏覽歷史、導出、去重檢查、手動總結等操作訪問原始記錄，不受 AI 可見範圍限制。
- ChatApp 主回覆在加載範圍後及最終請求組裝後檢查是否仍有有效 user/assistant 消息。自適應範圍為空可以是一鍵歸檔後的正常狀態，不據此讀取已歸檔原文，也不把通話/見面前的舊輸入當作待回覆消息。確無輸入時只提示再發一條消息，不要求用戶維護上下文設置，不改水位或記憶。本地聊天和即時對話上雲共用此保護，避免 system-only 請求觸發上游 `contents is not specified`。實現見 `utils/chatRequestGuard.ts`。
- 一次請求從原文加載到異步 prompt 構建共用同一份水位快照；構建中發生歸檔只影響下一次請求，不能讓已經加載的本輪消息被第二次過濾清空。新消息 ID 證明水位失效時，消息和 IndexedDB 水位鏡像在同一事務內提交/清理，再清 localStorage；後台鏡像校準也使用單個 assets 事務，避免舊值在清理後被寫回。正常水位與重複推送的已有消息不受影響。

手動區間總結面板按 IndexedDB 游標讀取一頁短預覽，全文/日期搜索按需掃描，可取消；不在打開面板時把全角色歷史和全文搜索副本裝進 React 狀態。確認起終點後，只讀取選區內的完整消息進行總結，水位線不變。

聊天設置和記憶宮殿的角色設置提供「清理指定範圍 / 保留最近 N 條」，獨立於總結和副 API：

- 範圍選擇使用同一分頁預覽（清理時也包含空消息），按起止消息 ID 選中該角色的全部私有記錄，包含兩個端點；搜索僅用於定位，不把刪除範圍縮成搜索結果。也可保留最近 N 條，N 至少為 1。
- 永久刪除必須經過兩個獨立彈窗。第一次核對角色、起止位置、實際條數和水位線之後的記錄數；第二次必須完整輸入「我確定永久刪除我選中的內容」，完全匹配才開放刪除。取消或重選會清空兩次確認狀態。
- 預覽只保留待刪 ID 和記錄指紋；讀取和校驗以 64 條為一批。確認期間新產生的消息保留；選中的正文或附屬內容已變化、消息已被刪除時，整筆操作回滾並要求重新預覽確認。
- 聊天原文、對應語音緩存及劇情副本引用在一個 IndexedDB 事務中處理。只對完全連續的已選 ID 合併刪除，避免跨過其他角色或群聊。已有記憶、收藏、中央劇情正文及其他角色副本保留，水位線和 AI 可見範圍設置不變。完成後刷新聊天窗口並標記主動消息雲端快照待同步。

關鍵實現：`components/chat/ChatHistoryCleanupModal.tsx`、`utils/chatHistoryCleanup.ts`；確認校驗、併發修改、跨角色隔離和十萬條清理測試在 `utils/chatHistoryCleanup.test.ts`。

### 二、存入邏輯（Input Pipeline）

```
角色統一消息時間線（私聊 / 見面 / 通話 / 劇情陪伴等來源共用）
    ↓
[最近N條] ← 熱區，直接在上下文中，不處理
[緩衝M條] ← 達到角色檔位閾值時觸發處理
[已處理]  ← 高水位標記之前的
```

#### Step 1 — 緩衝觸發

- 水位節奏按角色獨立保存於 `CharacterProfile.memoryPalaceWaterline`，隨 IndexedDB
  與完整備份持久化；舊角色缺少該字段時保持默認 `200 / 100`
- 三檔預設：線上為主 `200 / 100`、綜合 `100 / 50`、見面/劇情為主 `50 / 20`
  （前者為保留原文數，後者為觸發緩衝數），另支持小範圍自定義
- 管線只看同一 `charId` 下按 ID 排序的語義消息，不按來源建立多套水位線
- 觸發檢查不只在 ChatApp：私聊回覆、見面回覆、寫入角色時間線的劇情回合、
  通話開場/每輪回復/掛斷記錄落庫後都會在當前入口調用同一管線；主動消息、小屋、
  彼方寫入角色時間線後也會觸發。檢查本身不調用 LLM，只有緩衝達到當前角色閾值才整理
- `PROCESS_RATIO = 0.85`，處理85%，留15%尾部保持上下文連續
- 高水位標記（localStorage）記錄每角色處理進度，防重複
- 調快檔位後，已有緩衝會在下一次達到新閾值時處理，處理成功前不會先隱藏原文；
  調慢檔位不會讓高水位倒退或重複提取，原文窗口會隨新對話逐漸增長到新檔位

#### Step 2 — LLM 提取記憶（extraction.ts）

- 以角色第一人稱視角敘事，用戶稱"TA"
- LLM 輸出 JSON 數組，每條含：
  - `content`：第三人稱敘事
  - `room`：分配到哪個房間
  - `importance`：1-10（越高敘事越完整，含因→事→反應）
  - `mood`：happy/sad/angry/anxious/tender 等12種
  - `tags`：2-5個關鍵詞

#### Step 3 — 向量化（vectorStore.ts）

- 批量調用 Embedding API（batch=20），模型如 `text-embedding-3-small`，1024維
- **去重**：餘弦相似度 > 0.9 視為重複，跳過
- 寫入 IndexedDB：`MemoryNode`（embedded=true）+ `MemoryVector`（float[]）

#### Step 4 — 鏈接構建（links.ts）

- 自動規則（無需LLM）：
  - **時間鏈**：24h內創建 → strength 0.3-0.5
  - **情緒鏈**：相同mood → strength 0.4
- LLM 分類（輕量模型，temp=0.2）：
  - 類型：`causal` / `person` / `metaphor`
  - 強度 0.3-0.8

#### Step 5 — 鞏固：短期→長期（consolidation.ts）

- 客廳→臥室晉升條件：
  - importance ≥ 8 → 立即晉升
  - importance ≥ 6 且 age > 24h → 時間成熟晉升
  - accessCount ≥ 3 → 頻繁回憶晉升
- 客廳超200條 → 按有效重要性（importance × 衰減^小時）淘汰最低者到**閣樓**

#### EventBox 重新整合

- 自動壓縮仍是增量語義：同一未封盒事件的活節點達到 4 條時，用“舊整合回憶 + 新活節點”覆蓋 summary；累計事件達到 12 條後封盒。
- 事件盒展開頁提供手動“重新整合”：無論是否封盒，都重新讀取盒內全部 archived + live 原始節點，**不使用舊 summary**，用於修復總結遺漏或模型推理文本汙染。
- 手動重新整合不改變成員的 live/archived 狀態、封盒狀態和自動壓縮次數；會更新 summary 正文與 metadata、盒名/標籤，並強制為同一 summary memoryId 重新生成 Embedding。
- 新 summary 必須先成功生成向量才會覆蓋舊正文；輸出若含典型字數計算/推理過程會被拒絕並自動重試一次，兩次失敗則保留舊 summary。

#### 外部記憶搬家（最多 5 萬字）

給從其它應用、設備或記憶系統遷入的用戶提供兩條入口，共用
`externalMemory.ts` 的保真清洗規則：

- **神經鏈接 → 角色記憶 → 導入/清洗**：寫入傳統 `MemoryFragment`；
- **記憶宮殿 → 設置 → 從其它地方搬入原始記憶**：清洗後直接分房間，
  調用 Embedding API 寫入向量節點，並建立時間/情緒/人物/因果/隱喻關聯；
  同時複用全自動總結水位線的 `buildAutoArchiveFragments` +
  `mergePalaceFragmentsIntoMemories` 橋接邏輯，把同一批內容按日期寫入當前
  角色的神經鏈接傳統記憶檔案。

外部文本沒有聊天 `Message ID`，因此雙寫記憶但不推進
`mp_lastMsgId_*` / `hideBeforeMessageId`，也不會隱藏任何聊天記錄。

單次輸入上限 50,000 字，字數由前端按 Unicode 字符在本地統計。上限內按約
10,000 字的自然段邊界自動分批調用副 API；超過上限時不發起任何 API 請求，
而是按總字數建議需要拆成幾批，並提示優先在日期或完整事件段落之間切開。
提示詞的首要約束是“只整理時間和結構，不壓縮內容”：不得摘要、合併、
去重或省略人物、地點、數字、對話、動作、因果、順序與情緒細節；長事件
寧可連續拆成多條，也不能用一句結論替代原文。格式與保真是並列硬目標：
搬家路徑只接受完整 JSON 數組與完整字段契約，不使用通用解析器的截斷對象
搶救；輸出正文相對原批次明顯縮水時也會拒絕。格式/完整性失敗會自動重試
一次，仍失敗則整次不入庫並保留輸入，避免出現“前幾批成功、後幾批丟失”
的半份搬家。

### 三、檢索邏輯（Retrieval Pipeline）

**查詢源清洗（querySanitizer.ts）**：query 構建前先過 `sanitizeQuerySourceMessages`——圖片/表情包/語音消息整條剔除（圖片 content 是幾萬字符的 base64 data URI，進 embedding 批量請求會把 token 總量頂爆，硅基流動直接 400 code 20015），卡片類消息經 `normalizeMessageContent` 翻成可讀文本，文本里的 data URI 也一律剝離。入庫管線的 `isMessageSemanticallyRelevant` 是同一口徑。

**Embedding 請求防線（embedding.ts）**：單條截斷 4000 字符（防單條超 8192 token）；按批內字符預算（6000）+ 條數上限（10）切批（防「每條合法、合批總量超限」類 400）；批量仍被 400 拒時自動降級為逐條向量化並把完整錯誤響應寫進 console.error 日誌，逐條後仍失敗會在報錯裡指明第幾條、多長、內容開頭。**保險絲觸發必有用戶可見提示**：截斷、降級成功（"已恢復、結果完整"）都走 console.error 進設置裡的日誌面板（面板只捕獲 error 通道），有測試釘死不許靜默。

```
最近3條消息(≤500字) → 查詢構建
        ↓
   ┌────┴────┐
向量搜索(85%)  BM25關鍵詞(15%)    ← 混合檢索
   └────┬────┘
        ↓ 融合分數
   房間權重加權打分               ← 每個房間不同權重側重
        ↓
   擴散激活(Spreading Activation) ← 沿鏈接找關聯記憶，最多+5條
        ↓
   情緒啟動(Mood Priming)        ← 匹配當前mood的記憶×1.3
        ↓
   反芻檢查(Rumination)          ← 概率性從閣樓冒出1條創傷記憶
        ↓
   格式化輸出 → 注入System Prompt
```

#### 房間權重差異

| 房間 | 相似度權重 | 時近性權重 | 重要性權重 |
|------|-----------|-----------|-----------|
| 客廳 | 0.50 | 0.30 | 0.20 |
| 臥室 | 0.60 | 0.10 | 0.30 |
| 閣樓 | 0.70 | 0.00 | 0.30 |
| 書房/用戶房/自我房/窗台 | 0.55 | 0.15 | 0.30 |

#### 擴散激活（按角色性格）

- **感性型**：情緒鏈×1.0, 人物鏈×0.6
- **敘事型**：時間鏈×1.0, 人物鏈×0.8
- **意象型**：隱喻鏈×1.0, 情緒鏈×0.5
- **分析型**：因果鏈×1.0, 時間鏈×0.4

#### 輸出格式

檢索結果格式化為 Markdown，注入到系統提示詞：

```markdown

**[臥室 · 親密情感]** (2026-03-20, 重要性: 8)
TA第一次對我說……我當時心裡……

**[客廳 · 日常閒聊]** (2026-03-19, 重要性: 5)

```

上限12條記憶，每個話題盒最多展開3條兄弟記憶。

### 四、認知消化過程（高級仿腦機制）

#### 認知消化（digestion.ts）

每 50 輪聊天自動觸發 + 隨時可手動觸發（無冷卻限制）。觸發後在聊天界面彈窗反饋消化結果。消化是**純狀態機**——只改變現有記憶的狀態，不再向宮殿寫入概括：

- 閣樓創傷 → 解決（移入臥室）/ 加深 / 淡化
- 窗台期盼 → 達成（移入臥室）/ 失望（移入閣樓）
- 自我反芻 → 新困惑（新建閣樓節點，進入狀態機循環）

**回看窗口（消化的主輸入面）**：上次消化以來（`mp_lastDigest_` 時間戳）新增的客廳+臥室情景記憶（≤30 條，時間正序）作為 `[E*]` 材料——"聊天總結成一條條記憶，消化 = 回頭看這些記憶、二次悟出什麼"。產出走已有出路，帶硬上限（寧緊勿松，防閣樓通脹成焦慮症）：

- `worry`（≤2）→ 擔憂上閣樓，進狀態機循環
- `aspire`（≤1）→ 新期盼上窗台，進期盼生命週期
- `distill`（≤2）→ 跨時間穩定的二次領悟，帶 `plate_room` 提交對應門牌
- `keep` → 絕大多數經歷就只是經歷

概括類產出**改道門牌**（不再新建 MemoryNode——語義寫回情景庫會變成"泛情感高 imp 記憶"汙染召回，這是歷史上近似重複詞條的根源）：

- 書房知識內化 → 提交「我是誰」門牌
- 用戶信息整合（synthesize_user）→ 提交「TA的事」門牌
- 自我領悟（self_insight）→ 彈窗昭告保留 + 提交「我是誰」門牌。**不再追加 `char.selfInsights`**（該字段已凍結為只讀遺留，存量照常注入）

被消費的源節點打 `digestedAt` 標記退出候選池（舊數據靠衍生節點 sourceId 反查兜底）。

**消化日誌（DigestReport）**：每次消化落一條報告——審視了哪些材料、狀態機改了什麼、往門牌提交了什麼、門牌實際更新了哪幾塊。存 `digest_reports` 表（每角色留最近 30 條），記憶宮殿 App「認知消化」卡片裡可回看。

#### 期盼生命週期（anticipation.ts）

```
active(新建) → anchor(7天+，心理錨點) → fulfilled / disappointed
```

#### 共激活學習

多條記憶被同時檢索時，它們之間的鏈接強度 +0.05（最大1.0），模擬記憶網絡強化。

### 五、房間門牌（Room Plates — 情景→語義固化層）

**解決的問題**：房間裡存的全是情景記憶（帶時間戳的事件），走相似度召回是"抽卡"——對用戶的瞭解永遠碎片化，取決於本輪抽到什麼。人腦不是這樣：朋友不會去回憶"哪次談話你說過家裡的事"，他就是*知道*。缺的是情景記憶固化成語義知識的那一步。

**方案**：四個房間頭上各有一塊"門牌"（`room_plates` 表，`roomPlates.ts`）——房間裝原始經歷（召回細節），門牌寫沉澱出的常駐認知（每輪直接注入 System Prompt，不走召回、不衰減）：

| 門牌 | 房間 | 內容 | 上限 |
|------|------|------|------|
| 「TA的事」 | user_room | **角色卡測試**：把用戶當一張空白角色卡，只有必須寫在卡上的內容才收——基礎信息、家庭結構、重要他人、人格衝擊級的重大節點。階段性狀態/情緒分析/性格側寫不收（那是印象檔案的領域） | 12條 |
| 「我是誰」 | self_room | 角色對自己的穩定認知 | 10條 |
| 「我們之間」 | bedroom | 關係的**質地**。硬規則：禁止給關係命名（prompt 約束 + 合併層窄正則兜底） | 10條 |
| 「我的領域」 | study | 會什麼、在學什麼 | 8條 |

客廳天生短暫不配門牌；閣樓/窗台已有生命週期狀態機（本質就是它們的門牌）。

**更新時機（兩者都有）**：
- **EventBox 壓縮/封盒**（eventBoxCompression Step 9）→ 盒子結論增量合併進所屬房間的門牌。"進行中的線"活在盒子裡，封盒的結論才畢業成語義事實——邊界不是分類問題，是生命週期問題
- **認知消化**（digestion 尾聲，含無材料早退分支）→ 四塊門牌一次 LLM 調用全量整理

**合併語義**（`mergePlateEntries`，純函數可測）：LLM 每次輸出完整新列表，舊條目不被重新輸出即淘汰（硬容量上限 = gist 記憶的容量壓力，邊界判錯的條目會被自然擠出）；`basedOn` 引用舊條目則繼承 `firstLearnedAt` / `sourceCount+1`（保留"什麼時候得知的、被印證幾次"）。

**送達保證**：消化提交的候選（源節點已打 `digestedAt`，不會來第二次）在整理 LLM 失敗/輸出為空/漏掉某房間時**機械兜底併入**（`fallbackMergeSubmissions`：去重+容量+臥室規則照常，不改寫），絕不靜默蒸發；消化日誌裡"提交了但門牌沒更新"會顯示 ⚠️ 狀態行。

**長期用戶防灌爆**：消化候選池按時近取上限（書房/用戶房/自我房各 20 條、閣樓按重要性 12 條）——prompt 不被老積壓撐爆。

**老用戶歷史回填（Bootstrap）**：老積壓不白攢，但**只走手動**——記憶宮殿 App「整理歷史記憶到門牌」按鈕，**每按一次清一小段（5 批）**，進度存 localStorage（`mp_plateBootstrapBatch_`）斷點續傳，隨時可停、下次接著清，全部清完打 `mp_plateBootstrapped_` 完成標記。不做自動觸發：上千條記憶的用戶不該在毫無預期時看到一長串回填批次。機制：四個門牌房間的歷史按**時間正序**分批（12 條/房/批）過整理 LLM——後面的批次帶更新的事實，合併語義自然 supersede。每房間歷史上限 240 條（超出丟最舊）；合併冪等，重複回填不翻倍；每次 LLM 嘗試 120s 硬超時。

**注入**：`injectMemoryPalace` 每輪純 IDB 讀出 → `char.roomPlatesInjection` → `buildCoreContext` 在印象檔案之後注入（受 `memoryPalaceEnabled` 把關防殘留）。注入框架把門牌定位為 **constraint 而非 topic**："你早已知道的背景，不要主動提起，只在相關時自然影響反應"——對應人腦背景知識"常在但低激活"的狀態。

**審計**：神經鏈接 app「門牌」標籤頁（`RoomPlatePanel`）可查看/改寫/刪除——蒸錯的事實一旦常駐會被自信地重複很久，必須有人工糾錯口。一鍵清空（wipe）會連門牌一起清。

**備份**：門牌與消化日誌都隨「設置-導出」全量備份走（v2 分片，導出裝配在 OSContext、還原在 `importFullData`，clear-and-add 語義）；門牌另隨記憶宮殿導出/導入遷移（`export.ts`，合併語義：同文本去重、尊重容量上限、條目重生成 ID）。

## 本輪召回修補（記憶鏈接）

聊天加號面板的「記憶鏈接」用於修補剛才回覆實際使用過的記憶：

- `recallReceipts.ts` 記錄每輪真正注入 prompt 的 memoryId；修補入口只讀取當前用戶消息之後最近的一張回執，沒有回執時不會退回上一輪。
- 獨立記憶可直接原地修改；命中 EventBox 任一節點時，會展開盒摘要、全部活躍子節點和全部歸檔子節點，歸檔狀態不影響編輯。
- 修補現場顯示獨立記憶日期、事件盒日期範圍及每個盒內節點日期；盒摘要置頂，其餘活躍/歸檔節點按日期排列，診斷 API 也會收到每個候選節點的日期。當前可靠粒度是“日”，不展示常作為佔位值的 12:00，以免偽造精確時分。
- 保存補丁後用當前 Embedding API 為同一 memoryId 重新生成向量，並同步已啟用的遠程向量庫。
- 記憶宮殿詳情頁與「記憶鏈接」共用 `updateStoredMemoryNode`：正文沒變時只保存 metadata、零 API；正文變化時才發起一次單條 Embedding 請求。Embedding 失敗不會先寫入新正文，避免文本與向量失配。
- 「？？？」診斷顯式使用 `ContextBuilder.buildCoreContext(char, user, false)`；調用前清空舊制記憶、月度總結、向量召回注入、房間門牌與 buff。候選材料只來自本輪迴執及其命中事件盒的完整結構，不會再次調用向量召回。
- 「？？？」保持引路者身份，但診斷回覆借用當前角色的語言節奏與措辭；面向人時使用“你”或用戶名，提及當前角色時使用角色名字，不把雙方稱作“用戶/角色”。歸檔節點明確標記“已歸檔，本輪未注入”。
- 引路者形象直接複用角色在小屋裡的 `sprites.chibi`；沒有配置 Chibi 時才顯示光點。形象下只標“？？？”，不把引路者寫成角色本人。
- 引路者的進場問候和過場文案按角色 `personalityStyle` 從本地固定文案中穩定選擇，不調用 LLM；只有用戶主動描述錯誤並請求排查時才調用主 API。
- 顯影動畫可在入口右上角設置中永久跳過，偏好保存在 `os_memory_repair_skip_animation`。
- 打開入口時先關閉聊天加號面板；退出整個記憶鏈接時再次清空面板狀態，保證落回聊天正文。線索編輯抽屜的關閉只返回本次修補現場，不會丟失診斷結果。

關鍵實現：`components/chat/MemoryRepairPortal.tsx`、`utils/memoryPalace/memoryRepair.ts`。
